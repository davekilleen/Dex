# Dex Lens Catalogue Enrichment Design

**Status:** Lens `v0.1.9` released the compatible schema and verifier. Core's signed catalogue-v5 promotion is implemented; live publication follows the protected Core release path.

**Decision:** Phase 1 shipped the active-skill correction through the legacy-compatible
v2 shape. Phase 2 keeps the historical preview non-publishable and adds a distinct
`--enriched` production path, pinned to the exact Lens `v0.1.9` schema.

## Outcome

Dex Lens will stop comparing a person's system against a hand-picked, skills-only
subset of Dex.

Phase 1 publishes every active first-party skill through the existing Lens v2
contract. Phase 2 discovers skills, MCP servers, scheduled automations, and system
engines in one normalized model, ranks them, and produces both a permanently
unsigned example and the signed catalogue version 5 release payload accepted by
Lens `v0.1.9`.

## Verified Baseline

The baseline is canonical Dex Core `upstream/main` at
`489ea01cb7cbdfdf71238b9028f4107942d99771`.

- `scripts/generate-dex-lens-catalog.py` reads
  `core/lens-catalog/registry.json` directly and iterates only `registry["entries"]`.
  It does not scan the release tree for capabilities.
- The generator requires each resolved target to equal
  `.claude/skills/<entry-id>/SKILL.md`.
- `core/lens_catalog_sources.py` accepts only `active-skill`, `lifecycle-skill`,
  and `room-skill`. All three resolve to one `SKILL.md` payload.
- The repository contains 114 skill payloads: 66 active first-party skills,
  16 active vendored `anthropic-*` skills, and 32 dormant `_available/` skills.
- The registry contains 55 entries: 26 active skills and 29 dormant lifecycle or
  room skills. Exactly 40 active first-party skills are absent.
- The registry contains 11 job IDs. The canonical user-facing document contains
  eight jobs, although its section heading incorrectly says "The Six Jobs".
- The live v1.96.8 catalogue already carries an honest generation timestamp as
  `metadata.produced_at`. The current closed schema rejects an additional
  `generated_at` field.
- The current Lens schema and Pydantic model use closed capability objects and
  require every skill-shaped field. Adding `capability_class` is rejected as an
  unknown property.
- `core/mcp` contains 10 literal MCP servers exposing 131 tools. The separate
  Pipedrive integration server is outside this requested discovery boundary and
  is not included in that count.
- Four plist-backed automations ship under `.scripts`. The backup scheduler is a
  fifth scheduled capability generated by `core/backup/install_backup_job.py`.

## Non-Goals

- Do not change the current Dex Lens schema from Dex Core.
- Do not sign, publish, or serve the enriched four-class preview.
- Do not count vendored Anthropic skills as Dex capabilities.
- Do not describe dormant role or room skills as active.
- Do not describe `core/ritual_intelligence/` as live; repository architecture
  truth marks it as parked.
- Do not broaden MCP discovery to integration servers in this change.
- Do not make the catalogue generator mutate a vault.

## Phase 1: Complete Active-Skill Catalogue

### Discovery and annotation

Add one focused discovery module, `core/lens_catalog_discovery.py`. It scans only
direct children matching `.claude/skills/*/SKILL.md`.

The scanner:

1. excludes any directory named `_available`;
2. excludes every directory whose name starts with `anthropic-`;
3. rejects symlinks and non-regular `SKILL.md` files;
4. parses the skill name and description from frontmatter;
5. returns candidates sorted by skill ID.

`registry.json` remains the publisher-owned annotation source for judgment fields:
value, jobs, foundations, prerequisites, trade-offs, evidence, portable brief,
compatibility, documentation link, and release history. It no longer decides which
active skills exist.

Every discovered active skill must have exactly one active annotation. Every active
annotation must match a discovered skill. Either mismatch stops generation before
signing or writing output. This is the scan-then-annotate contract: discovery owns
existence; the registry owns meaning.

The 40 missing active skills receive complete annotations. Existing active entries
keep their reviewed prose unless the eight-job migration requires a job change.

### Dormant entries

The registry gains an internal `availability` value with the closed enum `active |
dormant`. Existing `lifecycle-skill` and `room-skill` entries are marked dormant.

The current v2 wire schema has no honest machine-readable dormant field. Phase 1
therefore emits only `availability: active` entries. Dormant annotations remain in
the registry for Phase 2, but they no longer pad the published active capability
count.

Phase 1's expected published set is therefore the 66 active first-party skills. The
exact count is asserted from discovery, not embedded as a permanent product limit.

### One eight-job taxonomy

The catalogue and both byte-identical system documents use these IDs and labels:

| Job ID | Label |
| --- | --- |
| `capture-without-friction` | Capture Without Friction |
| `start-each-day-focused` | Start Each Day Focused |
| `track-people-and-relationships` | Track People & Relationships |
| `manage-tasks-reliably` | Manage Tasks Reliably |
| `reflect-and-improve-continuously` | Reflect & Improve Continuously |
| `keep-projects-on-track` | Keep Projects On Track |
| `track-career-growth` | Track Career Growth |
| `evolve-the-system-itself` | Evolve the System Itself |

The stale "Six Jobs" heading becomes "Eight Jobs" in both canonical and bridge
copies. Every active and dormant annotation is remapped to at least one of these
eight IDs. The generator rejects any ninth ID or any unknown reference.

### Generation timestamp

`metadata.produced_at` remains the single generation timestamp in Phase 1. It is
already generated at build time, timezone-aware, signed, and required by Lens.

The schema-delta document will explicitly say that `produced_at` is the catalogue's
generation date. It will not add the redundant `generated_at` alias unless Dex Lens
chooses a future migration and defines precedence between the two fields.

### Phase 1 output and validation

The default command remains the only publishable path:

```text
python3 scripts/generate-dex-lens-catalog.py --release-root <release> --output-dir <output>
```

It builds the 66-entry active-skill catalogue and calls
`_validate_against_lens_schema` against the current vendored Lens schema before any
output is signed or written.

## Phase 2: Four-Class Catalogue and Guarded Preview

### Normalized candidates

The discovery module returns one immutable internal candidate shape with:

- `capability_id`
- `capability_class`
- `impact_tier`
- `availability`
- `title`
- `summary`
- `source_paths`
- class-specific metadata

Closed enums are:

```text
capability_class = active-skill | mcp-server | scheduled-automation | system-engine
impact_tier = core | high | medium | niche
availability = active | dormant | parked
```

`parked` is required so the ritual-intelligence engine can be represented without
being described as available. Skill entries use `active` or `dormant`.

Impact is publisher judgment and stays in registry annotations. Discovery must not
guess impact from file size, tool count, or directory position.

### MCP servers

Reuse the AST-based `discover_engines` logic already maintained by
`scripts/generate-architecture-inventory.py`, moving the shared parser into an
importable Core module if necessary. The Phase 2 boundary is
`core/mcp/*_server.py`.

For every file, discovery requires exactly one literal `Server("dex-...")`, at
least one exposed tool, and a list-tools handler. It records:

- server name;
- source path;
- exact tool count;
- up to five alphabetically stable example tools.

The baseline assertion is 10 servers and 131 tools. These numbers are drift alarms,
not permanent caps; any intentional change updates the reviewed fixture.

### Scheduled automations

Parse plist and plist-template files with `plistlib`. The four plist-backed entries
come from:

- `com.dex.changelog-checker` — every six hours;
- `com.dex.learning-review` — daily at 17:00;
- `com.dex.smoke-nightly` — daily at 03:15;
- `com.dex.meeting-intel` — every 30 minutes and at load.

Each entry records label, plist source, installer source, program target, and a
normalized cadence string. A missing installer or unsupported cadence stops preview
generation.

The fifth entry, `dex-vault-backup`, is resolved from
`core/backup/install_backup_job.py` and records its user-selected daily time. It is
not falsely presented as plist-discovered source.

### System engines

System engines do not have one uniform executable declaration, so discovery uses
closed, publisher-reviewed group annotations whose source patterns must resolve to
real tracked files:

- `entity-temperature-engine`: `core/entity_engine/`, especially temperature and
  cooling;
- `ritual-intelligence-engine`: `core/ritual_intelligence/`, marked `parked`;
- `proactive-promise-engine`: `core/health/promises.py` and its tests;
- `session-hook-orchestration`: the non-test `.claude/hooks/` layer.

Each group records all resolved source paths, component count, and up to five stable
example components. Unknown or empty patterns fail closed. The hook group excludes
`.claude/hooks/tests/`.

### Per-class source resolution

Replace the generator's direct dependency on `resolve_skill_source` with a class
dispatcher:

- skills continue through the existing release-owned skill resolver;
- MCP servers resolve one tracked regular Python source and verify the literal server
  identity and tools;
- automations resolve the tracked plist or generator plus installer target;
- system engines resolve the exact reviewed path set and reject symlinks, missing
  paths, test-only groups, and empty groups.

The final `.claude/skills/<id>/SKILL.md` equality check runs only for skill-class
entries.

### Guarded preview command

Add an explicit preview command-line mode:

```text
python3 scripts/generate-dex-lens-catalog.py \
  --enriched-preview \
  --lens-schema core/lens-catalog/schemas/dex-lens-catalogue-v2.schema.json \
  --output-dir <temporary-output>
```

Rules:

- `--enriched-preview` requires an explicit schema path;
- signing flags are rejected in preview mode;
- output filenames contain `preview` and cannot match release upload globs;
- the default generator remains available for the legacy Phase 1 compatibility proof;
- `_validate_against_lens_schema` receives the explicit schema and must pass before
  the preview is written;
- the checked-in example is generated against the exact released schema, never hand-edited.

Dex Lens `v0.1.9` now exports the agreed schema. Dex Core vendors that exact export,
pins its SHA-256 in tests, and exposes a separate `--enriched` release mode. The
preview command remains unsigned and writes a non-release filename; the stable
release workflow alone selects the enriched signing mode.

```text
python3 scripts/generate-dex-lens-catalog.py \
  --enriched \
  --sign \
  --output-dir dist
```

## Dex Lens Schema Delta

The implementation produces a separate exact schema-delta document for the Lens
repository. The model is a discriminated union keyed by `capability_class`, not one
large object with many nullable fields.

All four variants require:

- `capability_id`, `capability_class`, `impact_tier`, `availability`;
- `title`, `summary`, `value`, `jobs`, `evidence`;
- `release_provenance`.

The `active-skill` variant keeps every currently required skill field unchanged:
`prerequisites`, `trade_offs`, `compatibility`, `docs_url`, `since_release`,
`changed_in`, and `portable_brief`.

The three new variants use closed implementation fields:

- `mcp-server`: `server_name`, `source_paths`, `tool_count`, `example_tools`;
- `scheduled-automation`: `automation_label`, `source_paths`, `installer_path`,
  `program_target`, `cadence`, `run_at_load`;
- `system-engine`: `source_paths`, `component_count`, `example_components`.

Every variant has `additionalProperties: false`. The Lens Pydantic model uses a
discriminated union and regenerates the checked-in schema through
`scripts/export_catalogue_schema.py`. Lens tests must prove current skill entries
still parse unchanged, each new variant parses, cross-class fields are rejected,
unknown enum values fail, and the generated schema stays byte-equivalent to the
model export.

The existing complete cross-reference and unique-identifier validation remains
mandatory.

## Error Handling

Generation fails before signing or output when:

- an active skill lacks an annotation;
- an annotation names a missing or excluded source;
- a dormant capability would enter the Phase 1 wire output;
- a job reference is outside the canonical eight;
- a source is missing, symlinked, untracked, duplicated, or structurally inconsistent;
- an MCP declaration or tool set cannot be parsed exactly;
- an automation cadence or installer cannot be resolved;
- a system-engine group is empty;
- preview mode has no explicit schema or attempts to sign;
- either legacy or released enriched-schema validation fails.

The generator removes no existing release artifacts. As today, validation occurs
before writes so a failed run leaves nothing publishable behind.

## Test Strategy

Implementation follows red-green-refactor cycles.

Phase 1 tests prove:

- the pre-change catalogue misses 40 active skills;
- discovery includes all 66 first-party active skills and excludes 16 vendor plus 32
  dormant skills;
- discovery and annotation sets must match exactly;
- dormant registry entries cannot enter v2 output;
- the taxonomy is exactly the documented eight IDs;
- both Jobs-to-Be-Done documents remain byte-identical;
- the generated catalogue has the discovered active IDs in stable order;
- `produced_at` is present and no unsupported `generated_at` is emitted;
- the real registry builds and `_validate_against_lens_schema` passes.

Phase 2 tests prove:

- exactly 10 Core MCP servers expose 131 tools at the baseline commit;
- each MCP preview entry records count and examples;
- four plist automations and the backup scheduler resolve with honest cadences;
- all four system-engine groups resolve, with ritual intelligence parked;
- each per-class resolver rejects a wrong source shape;
- the historical Lens `v0.1.8` schema rejects the enriched example;
- the released Lens `v0.1.9` schema accepts the enriched example through
  `_validate_against_lens_schema`;
- a real Ed25519 test signature verifies through the released Lens wheel;
- the signed production mode emits catalogue version 5 through the normal versioned
  and `latest` release filenames;
- the example contains at least one entry of every class;
- preview mode cannot sign or create release-named artifacts.

## Delivery and Truthfulness

Phase 1 shipped as signed catalogue version 4 with 66 active skills and remains the
legacy compatibility proof for the Lens transition schema.

Phase 2 is implemented against the released Lens contract. Completion language must
still distinguish:

- Phase 1 implemented in Core versus actually merged or released;
- Phase 2 Core discovery implemented versus signed and served by a Core release;
- a generated example versus a signed published catalogue;
- parked system code versus live capability.

No customer-facing full-Dex claim is valid until catalogue version 5 is signed,
served from the canonical route, and accepted there by a released Lens build.
